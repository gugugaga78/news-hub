AI 第 12 课事件驱动与工具发现：让 Agent 自己醒来

2026-10-31 · 对应原书 第 4 章 §4.7-4.8（p128-140） · 用时 60-75 分钟 · 前置：0011 工具设计
🧭 你其实已经天天在用这一课的东西了：

· 每天 7:30，课程卡片自动出现在你手机上——没有人发消息，是 Agent 被「时间」叫醒的。
· 你发一句话，我回一句话——这是被「消息」叫醒。

事件驱动回答的问题是：Agent 怎么在你不说话的时候，自己动起来。

一、两种世界模型：拉 vs 推

请求-响应（同步）事件驱动（异步）
谁先动用户先开口外部事件先发生
人的体感问一句答一句它自己找你
生活类比打电话（必须在线等）收短信（可以稍后处理）
技术类比你每隔 5 分钟打开外卖 App 看骑手到哪了骑手到楼下，App 推一条通知给你
⚠️ 注意上面技术类比里那个蠢办法——它叫 轮询（polling）：每隔一会儿主动去问一次。
轮询的问题：问早了白问（费资源），问晚了迟到（信息慢）。绝大多数轮询的请求里，答案都是"还没变化"。
推模式的本质：没事的时候双方都安静；事情发生的那一刻，消息自动找上门

一个真实的对照

早期的网页聊天想知道"对方有没有回复"，只能让浏览器每隔几秒偷偷刷新一次（轮询），几千人在线时服务器大半的精力都在回答"没新消息"。改成 WebSocket/SSE 长连接（推模式）后，只有真有消息时才传数据，服务器负担下降一个量级。这不是新思想，是从"邮差每天挨家挨户敲门问你有没有信要寄"进化到"你有信时邮差才来"。

二、五种事件源：什么能叫醒 Agent

事件源什么时候触发你身边的例子
用户消息人发来文字/语音/图片你现在跟我聊天
定时器到了预设时间 / Cron 表达式命中每天 7:30 的课件推送
Webhook另一个系统通过 HTTP 主动回调支付成功了，支付平台回调你的服务器
文件/数据变更某个文件被创建、修改、删除数据表新增一行，自动触发分析
其他 Agent 的消息子任务完成、某个 Agent 发来结果你委派出去的子 agent 干完活回来汇报
事件的标准形状：事件类型 + 发生时间 + 相关数据（载荷）+ 唯一 ID
📝 看你每天 7:30 那条推送拆开长什么样：
· 事件类型：timer_fired（定时器命中）
· 时间：2026-10-31 07:30:00
· 载荷：今天星期几、该学哪科、章节和公式是什么
· 唯一 ID：保证这条事件不会被执行两遍（重启时尤其重要）

三、事件处理循环（这课的核心公式）

① 事件到达，进入队列排队
② 取出事件，加载相关上下文（历史记忆/用户画像/任务状态）
③ 决策（要不要动？怎么动？调什么工具？）
④ 执行（调工具 / 发消息 / 再产生新事件）
⑤ 记录状态（标记完成，写回记忆）

3.1 最难的一步：上下文恢复

同步对话里，上下文就在眼前；但被定时器叫醒的 Agent，面对的是一个"没有对话进行中"的世界。它必须自己回答：

  • 我是谁（当前是哪个 Agent/什么职责）
  • 我为什么被叫醒（事件载荷说明了什么）
  • 我上次干到哪了（从持久状态里恢复进度）
  • 该用谁的口吻、把结果送到哪里（推送到哪个聊天/平台）
⚠️ 这叫 wake + restore（唤醒与恢复）。判断一个异步 Agent 系统靠不靠谱，就看它重启或被重复叫醒时：会不会把同一件事干两遍、能不能从上次中断的地方接着走。

3.2 事件为什么要排队，不能直接处理

  • 削峰：100 个事件同时涌来，直接处理会把系统打趴；进了队列可以一个一个来
  • 解耦：发事件的人不需要等处理结果，更不需要知道是谁处理
  • 可重试：处理失败的事件可以重新排队，不会凭空丢失
  • 可审计：队列里每条事件的进出都有记录，事后能复盘"那天早上到底发生了什么"

四、工具发现：工具太多时的"按需检索"

接上 0011 的"挑战二"：当工具从几十个变成几百个，把全部定义塞进上下文有三重灾难——token 爆炸、模型选择困难、更新不同步。

解法：默认只给工具「名字索引」，需要时按任务检索相关工具的完整定义

4.1 工具发现的机制

① 每个工具有一段嵌入向量（它的名字+描述编码）
② 收到任务，把任务也编码成向量
③ 向量相似度排序，取 top-k 个最相关工具
④ 只把这几个工具的完整定义加载进上下文
⑤ 模型在这几个工具里做选择
tool = top_k( embed(task), tool_embeddings )
💡 这跟 0201/0202 里 RAG 检索知识是同一套数学——把"检索哪篇文档"换成"检索哪个工具"。检索层统一了：知识、记忆、工具，都可以按需召回。

4.2 原书数据

方式工具使用准确率
全部工具定义平铺（工具变多后）约 49%（干扰项太多，选择反而崩）
按需检索 + 只加载相关工具约 74%
⚠️ 反直觉点：给模型的信息更少，结果反而更准。因为决策质量不取决于选项总数，取决于"相关选项有多突出"。这跟人一样——菜单 200 道菜你反而不知道吃啥，给你 5 道合口味的，秒选。

4.3 事件驱动 × 工具发现怎么合体

这正是你想做的"本地 27B 接进 Hermes"的完整形状：

📝 一个真实链路：
1. 定时器叫醒（事件源=timer）
2. Agent 恢复上下文（今天该学哪科、你的进度）
3. 按任务检索工具——"生成课程"需要哪些？检索出 检索/写文件/发消息 三个，只加载这三个
4. 执行，把课程发到你微信
5. 如果本地模型没把握，再产生一个新事件："调用云端旗舰复核"
每一步都是事件驱动，每一件工具都是按需出现，没有一样东西全程占着资源。

五、异步 Agent 真正能干的事

场景事件链
监控哨兵定时跑检查 → 没变化就沉默（不打扰）→ 一变就产生事件 → 推送给你
长任务跟进子 agent 在后台跑 → 完成时发事件回来 → 主控汇总，而不是你盯着进度条等
多 Agent 流水线A 干完发事件给 B，B 干完给 C——像工厂传送带，每段只管自己那格
条件触发"如果明早下雪，提前 30 分钟叫我"——Agent 挂着监听天气，条件命中才醒
同步 Agent 的价值是"响应快"；异步 Agent 的价值是"一直在，但只在该出现时出现"

六、三条安全红线（做产品必须知道）

  1. 权限最小化：能自己醒来的 Agent 等于 7×24 持有能力——它的权限必须刚好够用，多一分都危险。尤其是"执行工具"，别让定时器触发的 Agent 直接有删除/付款权
  2. 事件可去重、可追溯：每条事件唯一 ID + 处理记录。防止"重启后重复执行"（比如重复推送、重复扣款）
  3. 自动动作要分两级：无害的（读、查、生成草稿）可以自动；不可逆的（发送给外部、删除、花钱、改动生产系统）必须留人工确认点
⚠️ 回忆你之前定的模型自进化三红线：人工确认键、测试集把关、一键回滚。这一课是同一套纪律在"异步"场景的翻版——Agent 越自主，确认和回滚的价值越高。

七、作业（这周做）

观察并记录你身边的一个异步系统，回答四个问题：

  1. 事件源是什么（定时器/Webhook/消息/数据变更）？
  2. 它被叫醒后怎么恢复上下文——它"记得"自己上次干到哪吗？
  3. 它的动作分了自动/人工两级吗——有没有不可逆动作被它自动执行了？
  4. 它会不会重复执行——如果系统重启，同一件事会不会发生两遍？
💡 最方便的观察对象就是每天 7:30 的课程推送本身。再进一步：等你把本地 27B 接进系统，试着让它"挂着监听、条件命中才醒"——比如只在某个数据变化时才汇报，而不是定时刷一遍。
