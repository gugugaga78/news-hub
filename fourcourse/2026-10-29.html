AI基础与理论事件驱动架构与工具发现

第 8 周 · 周四 · 2026-10-29 · 建议 60 分钟
🧭 一句话定位：Agent 不是只能「你问一句它答一句」。事件驱动让它能被消息、定时、文件变化唤醒——这才是「助理」和「聊天框」的分水岭。

本节要掌握什么

  • 拉模式（polling）vs 推模式（event-driven）：前者定时问，后者被动接
  • 事件源：用户消息、定时器、Webhook、文件变更、其他 Agent 的消息
  • 工具发现：工具太多时的动态加载机制（按任务检索相关工具）
  • 状态管理：事件驱动必须解决「上下文怎么接续」——事件来了，Agent 怎么知道之前聊到哪
  • 幂等与去重：同一事件可能重复推送，处理逻辑要能扛住
事件处理循环：收到事件 → 加载相关上下文 → 决策 → 执行 → 记录状态
工具检索：tool = top_k(embed(task), tool_embeddings)

推导 / 解题路径

  1. ① 列出所有可能唤醒 Agent 的事件源
  2. ② 为每类事件定义「需要什么上下文」
  3. ③ 设计状态存储：哪些进长期记忆、哪些只在本次事件有效
  4. ④ 加去重键（事件 ID），防止重复执行
📝 例题
Hermes 的 cron 就是事件驱动：到了设定时间，系统推送一个事件，Agent 被唤醒执行任务，跑完把结果推到微信。整个过程没有人主动提问——这就是「主动性」的工程实现。
⚠️ 事件驱动最容易出的问题是「上下文丢失」：事件来了，但 Agent 不知道历史。必须显式设计状态恢复，不能指望模型自己想起来。
💡 判断一个 Agent 是否「真助理」的标准：它能不能在你不说话的时候，因为某件事发生而主动做事。这就是事件驱动的价值。
