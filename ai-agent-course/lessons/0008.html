1. 一个更根本的问题：知识该怎么组织？

前面学的 RAG 基础技术（稠密、稀疏、混合检索）解决的都是：给定一个文本块，怎么快速找到最相关的那几个。

但还有个更根本的问题：这些文本块本身该怎么组织？ 把文档切成互不关联的扁平文本块，会丢掉知识固有的层次和跨文档关联——面对技术手册、法律文书、学术论文这类结构复杂的材料，只检索零散片段，「就如同靠阅读字典的随机词条去理解一部小说」。

两个反例（说明"平铺入库"为什么不够）

案例一：黑猫白猫的计数问题 知识库有 100 个独立案例文档（90 只黑猫、10 只白猫，每个是独立文本块），用户问"比例是多少？"——受限于 top-k（如 20），大部分案例根本检索不到，模型只能基于不完整样本（如 15 黑 3 白）得出错误结论。 ✅ 解法：预先提炼一条摘要「共有 100 只猫：90 只黑猫（90%）和 10 只白猫（10%）」并索引，一次检索就拿到准确信息。

案例二：Xfinity 优惠资格的边界问题 知识库是几百条客服工单，每条只记录一个个案的结论（退伍军人 John 通过、医生 Sarah 拿到折扣、教师 Mike 不符合），没有任何一条写着"资格范围本身"。护士来问"我能不能享受优惠"，三重障碍：

障碍 说明 调大 k 能解决吗
最近邻偏置 "护士"与"医生"语义最近 → Sarah 那条排最前 → 推断护士也可以；若 Mike 那条排更前，答案就相反 不能（甚至更糟）
边界语义缺失 "仅限…其他一律不适用"这种全称与否定的边界，不存在于任何单条工单里 不能
完整性信号缺失 模型无从判断自己是否看全，于是不追问、直接自信作答 不能

✅ 解法：离线通读整个工单库，提炼出一条规则卡「Xfinity 优惠适用于现役与退伍军人、持证医护人员（含护士）；教师等其他职业不适用」。

金句：两个案例指向同一结论——未经提炼和结构化的知识，模型都无法可靠地利用。无论存入向量库、检索后注入，还是直接塞进长上下文，都一样。因此必须在索引阶段投入计算资源，对原始知识主动提炼、抽象、结构化：把"100 个个体案例"压缩为统计摘要，把"散落在几百条工单里的个案"提炼为带边界的明确规则。

2. 结构化索引：从信息检索到知识建模 §3.3.1

思路：索引之前先用 LLM 把知识整理一遍——归纳、抽象、建立关联。多花计算资源，换更好的检索质量。业界两条主路：树状层次（RAPTOR） 和 实体关系图（GraphRAG）。

RAPTOR：自下而上递归抽象 → 知识树

叶子节点（小块）→ 聚类（语义相近分组）→ LLM 生成父节点摘要 → 递归
最终形成：从具体细节（叶子）到高度概括（根）的知识树
  • 聚类好比把图书馆的书按主题自动分堆：算每块之间的相似度，最相似的归一类，每一类代表一个主题
  • 例：关于 SSE 指令的多个叶子（"SSE2 支持 128 位整数运算""SSE4.1 新增字符串比较指令"）聚成一组 → 自动生成父节点摘要「x86 SIMD 指令集的各代演进」
  • 检索时跨层穿梭：先在高层摘要定位宏观概念，再沿树下钻到叶子找细节
  • 擅长："从概念逐步钻进细节"的查询

GraphRAG：实体-关系-实体三元组 → 知识图谱

三元组 = "主语-关系-宾语"，例：（北京, 是首都, 中国）、（张三, 就职于, 腾讯）。大量三元组交织成知识之网。

两大不可替代能力：

  1. 多跳关系推理 ⭐ 知识图谱最不可替代的能力 用户问"我的医生所在医院的地址"→ 需依次解析「用户 → 医生 → 医院 → 地址」这条关系链。扁平存储里：要么多次独立检索再由 LLM 拼接（效率低、易断链），要么根本无法表达；图结构天然支持沿关系边遍历。
  2. 实体消歧 ⚠️ 别和"一词多义"混：判断 "bank" 是河岸还是银行 = 词义消歧（靠上下文嵌入即可）；区分现实中两个同名的"张医生" = 实体消歧（需要维护实体本身的知识）。在图谱里，（张医生-A, 科室, 牙科）与（张医生-B, 科室, 心脏科）就是不同节点，消歧是图结构的原生能力。

GraphRAG 的致命局限：

局限 例子
语义降级（转三元组必然损失） "如果下周还下雨，我就取消去海边的计划，改成去博物馆" → 拆成三元组只剩（我, 有计划, 海滩旅行）+（我, 有备选计划, 博物馆旅行），条件逻辑和时间依赖全丢
提取准确性依赖 LLM 错误提取 → 知识污染

实践推荐 = 分层互补：以完整自然语言保存核心信息（保语义），辅以结构化元数据做索引检索（保效率）；在需要多跳推理和精确消歧的垂直场景（医疗问诊、法律案件、家族关系），把知识图谱作为专项索引，与自然语言记忆协同。

什么时候需要结构化索引？（成本敏感的判断）

你的查询类型 推荐方案
"找到包含某信息的文档片段"（如"退款政策是什么"） 混合检索就够了
跨文档综合（如"SSE 和 AVX 在架构上什么区别"） 结构化索引才值得
多层次导航（如"从整体架构逐步深入到具体指令"） 结构化索引才值得

代价：索引构建和查询都需要更多次 LLM 调用，成本和延迟显著增加——不是免费的午餐。

3. 文件系统范式：用目录结构组织知识 §3.3.2

RAPTOR / GraphRAG 是学术界的探索；字节跳动火山引擎开源的 OpenViking 提出第三种哲学：文件系统范式——不把上下文视为扁平向量碎片或图谱节点，而是把所有上下文（记忆、资源、技能）映射为虚拟文件系统的目录与文件：

viking://
├── resources/          # 外部知识：文档、代码库、网页
├── user/memories/      # 用户记忆：偏好、习惯
└── agent/              # Agent 自身：技能、经验
    ├── skills/
    └── memories/

viking:// 是虚拟 URI——类似 http:// 但不指向物理位置，框架背后决定从内存、磁盘还是远程加载。

核心设计：L0 / L1 / L2 三层按需加载 ⭐

层级 内容 体量 用途
L0 摘要 一句话概述 ~100 tokens 快速判断目录相关性
L1 概览 核心信息与使用场景 ~2,000 tokens 供 Agent 规划决策
L2 全文 完整原始内容 全文 仅在需要深入时加载

每个目录自动生成 .abstract（L0）和 .overview（L1）文件，形成从根到叶的层次摘要。L0 判定无关 → 不加载 L1/L2；大部分查询加载到 L1 就够决策 → Token 消耗大幅降低。

这套「摘要常驻、按需取全文」的思路，与第二章 Skills 渐进式披露 如出一辙——都是先让 Agent 只看到轻量元信息，确有需要再逐层拉取完整内容，把 Token 花在刀刃上。

为什么用 Markdown 纯文本，而不是专用数据库？

看似反直觉，实则深思熟虑：

  • 用户可直接阅读、编辑、修正 Agent 的知识
  • 可用 Git 版本控制与回滚
  • Agent 拥有 write_file 能力后，可在工作分支自主记录和组织知识，再经审核合入主库

⚠️ 最易被忽视的前提：文件之间必须有链接与索引

.abstract/.overview 解决的是纵向层次摘要，但还缺横向关联：若只是把知识拆成一堆独立文件平铺在目录里、彼此无交叉引用，除了逐个全文扫描或向量检索，Agent 几乎无从在相关条目间导航——知识越多，越难检索。

正确做法：把知识库组织得像 Wikipedia——每个条目提及他条时都以链接指向，再辅以入口页与索引页，让 Agent 顺着链接从一个概念走到相关概念。这相当于用轻量文件链接实现了 GraphRAG 实体关系图谱的一部分导航能力。

实践差异：不同模型主动建链接的意愿与能力差别很大。能力强的模型写入新知识时会自发回指已有条目、维护索引；不少模型只会孤立地追加文件。因此写入提示词里必须写明确：每新增一个条目，都要先检索并链接相关已有条目、更新目录索引页，形成双向可达的引用网络，而不是让知识退化成互不相连的孤岛。

4. ⭐ 联系 Hermes：这套东西你天天在用

书里的概念 Hermes 里的对应
L0/L1/L2 三层按需加载 skills 三级披露：系统提示词里每个 skill 只有一行 description（≈L0，判断相关性）→ skill_view(name) 加载 SKILL.md 全文（≈L2）→ 再 skill_view(name, file_path) 读 references/（更深的 L2）
文件系统范式（虚拟目录 + 统一路径引用） Hermes 的 workspace 目录 + memory 文件；我读写文件用的 read_file/write_file/search_files 就是这套"文件即知识"的操作面
知识必须有横向链接 skill 里的 related_skills 字段、memory 条目互相引用、SKILL.md 里指向 references/ 的链接——都是"条目间导航"
结构化索引（先提炼再索引） session_search 用 FTS5 全文检索历史会话；skills_list 的 description 就是给"该不该加载"用的轻量索引
"100 个案例压成统计摘要" 你的竞赛项目！82 例个案 → 聚类成 4 类融入形态 → 每类给统计画像，而不是让评委逐条读个案
规则卡（Xfinity 案例） 你项目里的政策知识库 + 10 条分级干预规则——正是"从散落个案提炼出带边界的规则"

最扎心的一个对应：你项目里的 search_cases / search_policy 现在做的是"扁平 RAG"（分块 → 向量检索）。如果升级成双层结构——上层存"案例统计画像卡 + 政策规则卡"（常驻上下文或优先检索），下层存原始个案明细（按需召回），那就是书里讲的结构化索引 + 双层记忆思路，检索精度会有质变。

5. 检索练习（先自己做，再看答案）

Q1：黑猫白猫案例说明了什么问题？正确的解法是什么？ Q2：Xfinity 优惠案例里的三重障碍分别是什么？为什么调大 k 解决不了？ Q3：RAPTOR 和 GraphRAG 分别擅长什么类型的查询？ Q4：GraphRAG 的"语义降级"是什么意思？举一个书里的例子。 Q5：文件系统范式的 L0/L1/L2 分别是什么？和 Skills 渐进式披露有什么共同点？ Q6：为什么"文件之间必须建立链接"这个前提这么关键？不建链接会怎样？

点击看答案（做完再看） A1：把大量原始案例平铺入库，top-k 限制导致只能检索到部分样本，模型基于不完整样本得出错误结论（如比例算错）。解法：在索引阶段先提炼统计摘要（"100 只猫：90 黑 90%、10 白 10%"）并索引，一次检索即可获得准确信息。 A2：①最近邻偏置（语义最近的个案排前，导致答案随排序而变）②边界语义缺失（"仅限…其他一律不适用"的全称/否定边界不在任何单条工单里）③完整性信号缺失（模型不知道自己没看全，不会追问）。三者都不是"多看几条"能解决的——问题在知识没有被提炼成规则，而非检索条数不够。 A3：RAPTOR 擅长"从概念逐步钻进细节"（跨层穿梭：高层摘要定位 → 树下钻取细节）；GraphRAG 擅长"A 和 B 之间是什么关系""谁和谁有关"这类关系性问题（沿关系边多跳遍历）。 A4：把自然语言转成三元组时不可避免丢失条件逻辑与时间依赖。书里的例子："如果下周还下雨，我就取消去海边的计划，改成去博物馆" → 拆成（我, 有计划, 海滩旅行）和（我, 有备选计划, 博物馆旅行），条件与时间全丢。 A5：L0=摘要（~100 tokens，判断相关性）、L1=概览（~2,000 tokens，规划决策）、L2=全文（深入时加载）。共同点：都遵循"摘要常驻、按需取全文"——先看轻量元信息，确需再逐层拉取，把 Token 花在刀刃上。 A6：没有横向链接，知识就是一盘散沙，Agent 除了全文扫描或向量检索外无从在条目间导航，知识越多越难检索。正确做法像 Wikipedia：条目互相链接 + 入口页/索引页，用轻量文件链接实现图谱的部分导航能力。

6. 速查卡（复习就翻这张）

  • 为什么结构化：平铺原始案例 → top-k 只看到部分样本 → 错误结论；必须在索引阶段提炼抽象
  • RAPTOR：叶子 → 聚类 → LLM 生成父摘要 → 递归成树；擅长"概念→细节"跨层检索
  • GraphRAG：三元组建图；两大强项（多跳推理、实体消歧）；致命局限（语义降级、提取污染）
  • 选择标准：碎片查询 → 混合检索够；跨文档综合 / 多层次导航 → 结构化索引
  • 文件系统范式：viking:// 虚拟 URI + L0（~100 tok）/L1（~2k tok）/L2（全文）三层按需加载
  • Markdown 纯文本：可读可改 + Git 版本控制 + Agent 自主写入
  • ⚠️ 建链接是前提：条目互相链接 + 索引页，否则知识越多越难检索
  • ⭐ Hermes：skills 的 description（L0）→ SKILL.md（L2）→ references（更深）= 渐进式披露
